# Работа с Go-проектом

Перед изменением прочитай задачу, затрагиваемый код, его вызовы и `go.mod`.
Используй существующие команды проверки из Makefile и CI, если они есть.
Версию языка и доступность API определяй по `go.mod` и инструментам проекта;
не обновляй Go или зависимости только ради примера из скилла.

Правила проекта и скиллы дополняют друг друга в своих областях. Ограничение
проекта не отменяет полезные рекомендации скилла по остальным вопросам.
Примеры скилла не вводят требования к поведению продукта, архитектуре или стеку.
Если задача явно меняет соглашение проекта, обнови соответствующий источник.
При неустранимом противоречии, влияющем на результат, обозначь его пользователю;
обычный выбор реализации решай самостоятельно.

## Слои

Доменные сущности, валидация и ошибки находятся в `internal/domain`.
Простые прикладные операции группируются в `internal/usecase/<сущность>`:
один `Usecase` с методами операций и один интерфейс репозитория. Сложная
операция выделяется в `internal/usecase/<операция>` по критериям usecase.md;
в ней остаются `Usecase`, `New` и `Do`. Интерфейсы зависимостей объявляются
в `interface.go` потребителя, параметры методов именуются.
HTTP находится в `internal/api`, хранение и запросы — в `internal/repository`. Отдельного пакета query для CRUD задач нет.
Результаты Bob преобразуются в доменные типы без копий readmodel.
Общая инфраструктура PostgreSQL находится
в `internal/storage/postgres`. Не объединяй домен и use case в один пакет.

## Генерация и миграции

Никогда не используй `.gen.` в именах файлов. Генерируемый код обновляй
только через `make generate`; вручную меняй исходные контракты и конфиги.
Не добавляй поясняющие комментарии в написанный вручную Go-код.
В SQL-миграциях комментариями `--` объясняй неочевидные связи и порядок действий.
Пояснения пиши короткими предложениями на русском.
Названия полей, типов и сущностей используй как в коде, например `id` и `workflow`.
Не заменяй их переводами или длинными описаниями.
В тексте комментариев не используй точки с запятой, двоеточия и длинные тире.
Имена из кода и служебные метки генераторов сохраняй.
Изменения разных частей схемы разделяй на отдельные файлы Goose.
Миграции пиши только вперёд, без секции `Down`. Не добавляй индексы впрок.
Ограничения PRIMARY KEY, UNIQUE и FOREIGN KEY используй для целостности данных.
В OpenAPI оставляй поясняющие тексты только в `summary`. Обязательные
`description` ответов оставляй пустыми.

## Команды

Выполняй команды из корня репозитория.

| Задача | Команда |
| --- | --- |
| Применить форматирование | `make fmt` |
| Проверить конфигурацию линтера и код | `make lint` |
| Собрать исполняемые программы | `go build ./cmd/...` |
| Запустить все тесты | `go test ./...` |
| Запустить сервис | `go run ./cmd/service` |

Для проверки конкретного пакета передай его путь в `go test`.
Необходимые настройки окружения и внешние сервисы уточняй по документации и конфигурации репозитория.

## Завершение работы

После изменения Go-кода выполни `make fmt`, `make lint` и проверки затронутого
поведения. При изменении точек входа или сборки дополнительно выполни
`go build ./cmd/...`. Не ослабляй линтер и не меняй ожидания теста лишь ради зелёного запуска.
В результате коротко укажи изменение, выполненные проверки и оставшиеся
ограничения. Невыполненную проверку не называй успешной.
